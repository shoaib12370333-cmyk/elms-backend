# ELMS Production Setup

This build is configured to use eBay Production when `EBAY_ENV=production` (or when `EBAY_ENV` is omitted). Sandbox remains available by setting `EBAY_ENV=sandbox`.

## eBay Production

1. In the eBay Developer Portal, create/use the **Production** keyset.
2. Assign these OAuth scopes to the keyset (must match `services/ebayUserAuthService.js` `SCOPES` and the duplicated inline copy in `services/ebayAuthService.js` exactly - see the warning comment in that file):
   - `https://api.ebay.com/oauth/api_scope`
   - `https://api.ebay.com/oauth/api_scope/sell.inventory`
   - `https://api.ebay.com/oauth/api_scope/sell.account`
   - `https://api.ebay.com/oauth/api_scope/sell.fulfillment`
   - `https://api.ebay.com/oauth/api_scope/sell.finances`
   - `https://api.ebay.com/oauth/api_scope/commerce.identity.readonly`
   - `https://api.ebay.com/oauth/api_scope/commerce.message`
   - `https://api.ebay.com/oauth/api_scope/commerce.notification.subscription`
3. Configure the Production RuName's accepted-auth URL to:
   `https://YOUR-BACKEND-DOMAIN/api/ebay-connect/callback`
4. Set `EBAY_ENV=production` and use the Production Client ID, Client Secret, and RuName.
5. Reconnect every existing eBay account after changing scopes so the new consent is stored in its refresh token.

## Disconnecting an eBay account is now non-destructive

**Before this change, "Disconnect" in Settings permanently deleted everything ELMS kept for that store** (`models/ebayAccountsModel.js` `purgeStoreData`: every listing/draft, order, message/conversation, import, notification - a hard `deleteMany`, not a soft delete). A seller who disconnected and reconnected the same store to pick up a new OAuth scope (e.g. `sell.finances` above) lost their entire Drafts/Live listings/Orders/Messages history for it - the live listings on eBay itself were never touched, but ELMS's own copy of everything about them was gone. This is why every seller had to be told, clearly, to reconnect WITHOUT pressing Disconnect first.

**Disconnect is now soft**: `EbayAccount.disconnectedAt` is set (row and all its data kept exactly as they are) instead of deleting anything. A disconnected store:
- Is hidden from every "combined, every store" view (`models/listingsModel.js`, `models/ordersModel.js`, `models/conversationsModel.js` `excludeDisconnectedAccounts`) - Drafts, Live listings, Orders, Messages. Asking for that ONE store by its account id still shows its data (nothing to hide from the seller who explicitly wants to look at it).
- Is excluded from every background job's account loop (`jobs/orderSync.js`, `jobs/orderEarningsSync.js`, `jobs/conversationSync.js`, `jobs/statsSync.js`) - a disconnected store is never synced or charged for sync while disconnected.
- Does not count against the seller's eBay-account connection limit (`getAccountLimitStatus`).
- Shows in Settings with a "Disconnected" badge and a "Reconnect" button (the same OAuth flow as "Connect an eBay account" - `addEbayAccount` matches by `ebayUserId` and, finding the disconnected row, clears `disconnectedAt`, makes it active again, and everything reappears immediately across every page).

`models/ebayAccountsModel.js` also exports `permanentlyDeleteEbayAccount` - the OLD destructive behavior, kept for a genuinely-final "forget this store forever" action, but it is **not wired to any route or UI button** as of this change (Settings' "Disconnect" always calls the safe `removeEbayAccount` now). Wire it up deliberately, with its own clear warning, if/when that's actually needed.

**Recovering data already lost by an old, destructive disconnect** (before this fix shipped) is not something the app can do - if that happened, check whether the MongoDB hosting plan keeps automatic backups (e.g. MongoDB Atlas M10+ clusters have continuous backups under the cluster's "Backup" tab) and restore from a snapshot taken before the disconnect.

## Business Policies and location

Every live Inventory API offer needs a payment policy, fulfillment/shipping policy, return policy, and an inventory location. ELMS can fetch policies and locations from eBay in Settings. eBay requires these for publishing live offers.

## Order sync

- Polling mode: periodic Fulfillment API sync, with a configurable per-user interval.
- Real-time mode (free, no daily credit fee): the same polling safety net plus the signed eBay `ORDER_CONFIRMATION` webhook endpoint. Only the polling-only mode is charged (`ORDER_SYNC_POLLING_DAILY`).
- The webhook endpoints (mounted in `server.js`) are `/api/ebay/order-notification` (ORDER_CONFIRMATION), `/api/ebay/message-notification` (NEW_MESSAGE) and `/api/ebay/account-deletion` (Marketplace Account Deletion, required by eBay). Each one answers eBay's `challenge_code` check with SHA-256(challenge code + verification token + the exact public endpoint URL), and each needs its own two environment variables: `EBAY_ORDER_NOTIFICATION_VERIFICATION_TOKEN` + `EBAY_ORDER_NOTIFICATION_ENDPOINT_URL`, `EBAY_MESSAGE_NOTIFICATION_VERIFICATION_TOKEN` + `EBAY_MESSAGE_NOTIFICATION_ENDPOINT_URL`, `EBAY_ACCOUNT_DELETION_VERIFICATION_TOKEN` + `EBAY_ACCOUNT_DELETION_ENDPOINT_URL`. Without them eBay cannot verify the endpoint (a GET with a `challenge_code` answers 500 and says which variable is missing).
- Until the order-notification variables are set AND eBay has a subscription for the seller, there is no live order feed: "real-time" users are then synced by the safety-net poll at their chosen interval (still free).
- eBay user-based notification subscriptions require the notification subscription OAuth scope and a public HTTPS endpoint. The actual eBay subscription still needs to be created/enabled in eBay's Notification API/developer workflow unless an approved subscription-management workflow is added.

## Tracking conversion

`POST /api/orders/tracking/convert` normalizes common carrier names into eBay carrier codes. When tracking is saved through `PUT /api/orders/:id/tracking`, ELMS converts the carrier and sends the fulfillment update to eBay.

## Auto Order limitation

The Auto Order credit/feature label is retained, but this build does **not** pretend to place retail Amazon purchases automatically. Amazon's public seller APIs are not a generic retail checkout API for buying arbitrary Amazon retail products for eBay customers. A real unattended procurement implementation requires a supported supplier/retail ordering integration (with the required account authorization and terms). ELMS therefore keeps this part fail-closed rather than using browser automation, CAPTCHA bypasses, or fake order IDs.

## Security before going live

- Replace `ENCRYPTION_KEY` with a long random secret.
- Replace `JWT_SECRET` with a long random secret.
- Rotate any credential that was ever pasted into chat/screenshots.
- Use HTTPS only for `FRONTEND_URL`, RuName callback URLs, and notification endpoints.
- Do not commit `.env`.

## Visitor IP address

On Render a request travels visitor -> Cloudflare -> Render's proxy -> ELMS. `config/trustProxy.js` skips Cloudflare's published address ranges (and internal addresses) so `req.ip` is the visitor; the IP limits, IP blocks, the new-accounts-per-network guard and the sign-in location depend on it. After a deploy, sign in once from your own phone and check that Settings -> Security shows YOUR public IP (not a `172.6x`, `104.x` or `162.158.x` Cloudflare address). If it still shows a Cloudflare address, set `TRUST_PROXY_HOPS=2` on Render (a fixed hop count) and tell us. An IP you blocked earlier that was really a Cloudflare address no longer matches anyone: remove it in the admin panel.

## Sign-up email checks

`POST /api/auth/register` refuses example/test addresses, temporary-mail services (built-in list; add more with `BLOCKED_EMAIL_DOMAINS=a.com,b.net`), typos of the big providers and domains without mail (DNS lookup; a slow or failing lookup lets the sign-up through).

## Sign-up confirmation code

Sign-up with a password is two steps: `POST /api/auth/register` mails a 6-digit code (valid 15 minutes, 5 tries, a new code at most once a minute, at most 5 sign-ups per address per hour) and remembers the sign-up in `PendingSignup` (it disappears by itself after 24 h); no account exists yet. `POST /api/auth/register/confirm` with the code and the browser's `pendingToken` makes the account, gives the welcome credits, mails the welcome mail and signs the person in. So password sign-up needs a working SMTP (`SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`), the same as "Forgot password"; Google sign-up does not. Accounts from before this change are untouched.

## eBay call budget (many stores)

eBay gives the whole application a fixed number of Trading API calls per day (5,000 by default, shared by every seller). Views and watchers are the only thing read again and again, so `services/ebayCallBudget.js` keeps a daily count in MongoDB (`ApiUsage`, one row per Pacific-time day) and gives statistics 70% of it; order pictures, buyer profiles and the connect step are counted but never refused. A store is read with `GetMyeBaySelling` (200 listings per eBay call), never one call per listing. When the day's share is used up the background job (`jobs/statsSync.js`, every 30 minutes) stops and the Live listings page keeps showing the last numbers; stores whose owner has not opened ELMS for 14 days are skipped until they come back. Opening the page or pressing the sync button asks eBay at most once every 2 minutes per store.

Set `EBAY_TRADING_DAILY_LIMIT` (default 5000) when eBay raises your limit (Application Growth Check) and `EBAY_TRADING_STATS_SHARE` (0.1-1, default 0.7) to change the share. Admin -> `GET /api/admin/ebay-usage` shows today's numbers and what the last run did (`viewsInBulk: false` means eBay's bulk answer has no view counts, so views are refreshed a few listings at a time instead).

## Order earning, auto-filled from eBay (Sell Finances API)

`Order.orderEarning` (the Net Profit sheet's "what eBay pays out for the order") used to be typed by the seller by hand; it is now fetched automatically from eBay's own Sell Finances API instead - the Orders page no longer has a box to type it into (only "Buy cost" is still typed, since ELMS has no source for that number).

- **⚠ Every seller must reconnect eBay**: this needs a new OAuth scope (`sell.finances`), added to `services/ebayUserAuthService.js` `SCOPES` and `services/ebayAuthService.js`'s duplicated inline copy (the two must stay in sync - see the warning comment already in that file). A refresh token issued before this change does **not** carry the new scope; every already-connected seller must press "Connect an eBay account" again (the same account, from Settings) before their orders' earnings start filling in. Until they do, `jobs/orderEarningsSync.js` logs one line per account (`likely needs to reconnect eBay for the new Finances permission`) and moves on - it never crashes and never retries every pending order individually.
- **Why not `getOrderEarnings`** (the Finances API method that hands back a ready-made "net earning" figure directly, no manual fee math needed): per eBay's own docs, that resource needs a separately eBay-approved "application growth check" and is currently limited to US/China/Hong Kong sellers with a USD payout - not available generally. `getTransactions` (used here) needs no special access.
- **The calculation** (`services/ebayFinancesService.js`): `GET /sell/finances/v1/transaction`, filtered to `orderId:{...}` and `transactionType:{SALE}` (two separate `filter=` query params - eBay's docs combine filters that way, never one comma-joined string), with the required `X-EBAY-C-MARKETPLACE-ID` header (Fulfillment API calls don't need this header; Finances calls do). `Transaction.amount` is documented as the transaction's own net dollar value - already after eBay's fees for a `SALE`.
- **Multi-item eBay orders**: ELMS keeps one `Order` document per line item (per SKU), but eBay's fee data here is fetched once per whole eBay order. When one eBay order has several ELMS line items, its single fetched earning is split across them proportional to each line's own `salePrice` (`jobs/orderEarningsSync.js` `splitProportionally`) - a reasonable approximation, not eBay's own per-line breakdown.
- **Not built yet (v1 limitation, deliberate)**: refunded/partially-paid orders are skipped entirely (`ebayPaymentStatus` must be `PAID`) - a returned order's earning is never auto-filled, and is not netted down if a refund happens after the earning was already filled. A seller can still type a correction in the Net Profit sheet by hand for such a case (the PATCH endpoint and UI there are unchanged); `setOrderEarningsBulk` never overwrites a value that is already set (auto-filled or manually typed), so a manual correction is never silently clobbered by a later sync run.
- **Timing**: `jobs/orderEarningsSync.js` runs every 5 minutes and tries an order from the moment it is paid (`MIN_AGE_MS = 0`) - eBay not having a settled Finances transaction yet just means the order is silently left for the next run, so trying early costs nothing.
- **2026-09-29, found and fixed against real production data**: eBay's `OrderPaymentStatusEnum` has no `FULLY_PAID` value (confirmed against eBay's own published enum docs) - the real value is `PAID` (others: `FAILED`, `FULLY_REFUNDED`, `PARTIALLY_REFUNDED`, `PENDING`). The original code/tests were built and tested only against a fake standing in for eBay that used `FULLY_PAID` too, so nothing caught it: `listOrdersNeedingEarnings` matched zero real orders from the day this shipped. A read-only check of the real `elms` database confirmed it - `ebayPaymentStatus` across all 725 real orders was only ever `PAID`, `FULLY_REFUNDED` or `PARTIALLY_REFUNDED`, never `FULLY_PAID`; 56 real `PAID`/`FULLY_REFUNDED` orders had `orderEarning: null` and would never have been picked up. Fixed in `models/ordersModel.js` `listOrdersNeedingEarnings`. Still to verify after this deploys: check the Render log for a `[order-earnings] Filled in eBay earnings for N order line(s).` line, then compare the filled-in figure against Seller Hub's own "Order earnings" number for that same order.

## More eBay reads (selling limit, listing problems, usage)

Three read-only eBay APIs feed the panels; none of them needs a new permission or a reconnect. **Selling limit** (Account API `getPrivileges`) and **listings that break an eBay rule** (Compliance API, e.g. missing item specifics) are asked with the seller's own token, remembered for 30 minutes and shown under each store in Settings (`GET /api/ebay-accounts/:id/status`, `/violations?type=`) and as a banner on Live listings. If eBay answers 401/403 for a store (connected before the permission existed, or the Compliance API is not open to the app) the store just shows "eBay status not available". **eBay API usage** (Analytics `getRateLimits`, with the application token) is in Admin -> Settings next to ELMS's own Trading count; the app needs its normal `EBAY_CLIENT_ID` / `EBAY_CLIENT_SECRET`.

## Pricing rule (Settings > Pricing)

A seller can save one pricing rule (`GET/PUT /api/pricing/rule`, `POST /api/pricing/preview`): fees % and fixed fee, profit % and fixed profit, a minimum profit, an amount for shipping, the cents the price must end in and cost-range ("dynamic") profit tiers. The price is `(cost x (1 + profit%) + fixed profit + fixed fee) / (1 - fees%)`, in whole cents (`services/pricingService.js`; the same maths as the Price Calculator).

It prices a product **only when it is switched on and the request has no markup % of its own**: the single import, the extension's import and the background list. A markup typed on the Import page (or sent by an older extension) always wins and works exactly as before; with no rule, or a rule that is off, nothing changes. A rule that cannot be used (a broken saved rule, or a rule in another currency with no exchange rate right now) refuses the import (409 / 503) before any credit is taken. A background list keeps the rule of the moment it started (`BulkImportJob.pricingRule`). A draft keeps a copy of its rule (`Listing.pricingRule`, money in the listing's currency): the stock monitor then re-prices it by the rule instead of keeping the cash margin, and a price typed by hand ends the rule for that listing. Existing drafts and live listings are never touched by saving a rule.


## Suspend, permanent ban, appeals and account mails

Admin -> Users -> Security: **Suspend** (the person can appeal from the blocked screen) or **Permanent ban** (`permanent: true`: no appeal, `POST /api/appeals` answers 403 for that account). Both mail the person the reason; **reinstating** mails them too. A permanent ban can only be reinstated with a message of 10+ characters (checked on the server), and that message goes into the mail. The mails go out from the **Security** sender (`SMTP_FROM_SECURITY`, or the default sender when it is not set up), replies go to Support. If the mail cannot be sent, the action still happens and the admin is told ("the email could not be sent").

Appeals are support tickets with source `appeal`. **Admin -> Appeals** lists them (open first, with the state of the account); a person who already has an open appeal adds to it instead of opening another. Reinstating an account closes its open appeals.

Every ELMS mail carries the same layout and the Privacy Policy / Terms links (`/privacy`, `/terms`): `mailTemplate.ensureLayout` runs on every message inside `emailService.sendWithTimeout`, so a mail written without the layout still gets it, and `tests/banAppeals.test.js` fails if a new `send...` function has no sample there.

## Large imports (bulk jobs) and the Easyparser per-minute limit

A background list can hold up to **2500 links** (Admin -> Limits -> `bulkJobMax`; 2500 is the highest it can be set to and the default; a lower value saved earlier stays until you change it). The processor runs once a minute and, per job, sends at most 90% of the plan's per-minute limit to Easyparser and reads and saves at most the limit's worth of finished products (`EASYPARSER_PER_MINUTE`, default 500 = our plan). Sending everything at once made Easyparser answer "rate limit" for all but the first 500, and the rest were given up on after 5 tries; now a run that got anything through does not count as a failed attempt. 2500 links take about 6 runs (about 6 minutes plus Easyparser's own time); set `EASYPARSER_PER_MINUTE` if the plan changes.

## Publish all (batches), notifications and how many publish at once

`POST /api/listings/publish-batch { ids }` starts a whole selection in ONE request (up to 2000): every draft is claimed and put in line for the background publisher and the answer comes at once (202, with `started` and the reason for each one that was not started). `GET /api/listings/publish-batch/:id` gives the counts (published / failed / still publishing). When every listing of a batch has finished, the person gets ONE notification in the bell (also with the page closed): how many went live and how many failed (the once-a-minute publish job sends it; it is marked atomically, so it is never sent twice).

`PUBLISH_CONCURRENCY` (default 6, or 30 with bulk publishing on; at most 50): how many publishes run at the same time for the whole server. eBay answers "system error" when it is hit with too many at once, so raise it slowly and watch the failed count. A listing that is waiting in the server's line is never failed as "interrupted" any more (that used to happen after 30 minutes for the ones at the back of a long list); only a listing that nothing is working on and nothing is waiting for is.

## eBay bulk publishing (`EBAY_BULK_PUBLISH`)

One listing published the old way is four eBay calls (inventory item, look for an offer, create offer, publish). eBay's Inventory API takes **25 of each step in one call** (`bulk_create_or_replace_inventory_item`, `bulk_create_offer`, `bulk_publish_offer`), so 1000 listings are about 120 calls instead of about 4000. With `EBAY_BULK_PUBLISH=1` the publish worker sends the first attempt of each listing through `services/ebayBulkPublisher.js`: listings that ask at about the same time (same eBay store and marketplace) are collected for a moment (`BULK_PUBLISH_WINDOW_MS`, default 1500) or until 25 are there, and go together. The worker itself is unchanged (credits, checks, refunds, notifications); it only runs more listings at the same time (`PUBLISH_CONCURRENCY`, default 30 when bulk is on, at most 50).

**Off by default.** The shapes of the three calls follow eBay's Inventory API model documentation, but they have not been run against a real store from here. Turn it on like this: 1) set `EBAY_BULK_PUBLISH=1` on the backend, 2) publish 3 to 5 drafts of ONE store, 3) look at the Render log for `[bulk-publish] group of N: ...` and check the listings are live on eBay, 4) then publish a bigger selection. Set it back to `0` (or remove it) to return to the old way at once.

Safety: whenever anything is unusual, that listing goes the ordinary one-at-a-time way, which already reuses an existing offer: a bulk call that fails as a whole (timeout, 5xx, 429, an answer that cannot be read), an offer that already exists, an answer that is missing for a listing, or the same SKU twice in one group. A listing eBay really refuses (a missing item specific ...) fails with eBay's own words, as before. A retry after a transient eBay error is always one listing on its own.

## Live listings: Change price (many at once)

`POST /api/listings/bulk-live-price { ids, changes: { price: { mode: 'saved' | 'custom', rule } } }` (up to 500 per request; the page sends 100 at a time, three requests at once). The new price of each LIVE listing is worked out from its own Amazon price by the pricing rule (the same code as the Drafts bulk edit) and sent to eBay with `bulk_update_price_quantity`: **25 prices per call, four calls at a time** (`services/liveBulkPriceService.js`), so 1000 listings are about 40 eBay calls. Only after eBay took a price does ELMS save its copy (with the rule, so the price monitor keeps using it). Anything unusual (the whole call fails, an offer is missing from the answer, an offer is refused) sends that listing the ordinary way (`updateOfferPrice`), which sets the price or fails with eBay's own words; that listing is then reported as skipped with the reason. No flag: the fallback makes a wrong call shape slow, never wrong. The Render log shows `[bulk-price] N prices for eBay in G group(s): X in bulk, Y one by one, Z refused.`; if `in bulk` is 0 on a big run, the bulk call itself is being refused and only the slow path is working.

## "The UPC field is missing" (eBay error 25002)

Some eBay categories want a barcode (UPC / EAN / ISBN); ELMS has none for an Amazon product. Nothing is sent for a barcode by default, so a listing that publishes fine is left exactly as it was. When eBay answers that an identifier is missing ("The UPC field is missing. Please add UPC to the listing and try again."), that one listing is published once more, at once, with `product.upc` (or `ean` / `isbn`, whichever eBay named) = `["Does not apply"]`, eBay's text for a product without a barcode (`services/productIdentifiers.js`, used by `publishOnEbay`; it works for the bulk and the ordinary path). If eBay still refuses, its own message is shown on the draft as before (for example that the barcode itself is not valid): that category then needs a real barcode. Listings that already failed with this message go through again with **Retry**.

## eBay Taxonomy API: fewer calls (daily limit 5,000 for the whole application)

Every Taxonomy call (category suggestion for a title, the item specifics of a category, a category's name and leaf status, a marketplace's tree id) counts against eBay's daily limit. `services/ebayTaxonomyService.js` now asks eBay for the same thing only once: answers are kept in memory **and in MongoDB** (`TaxonomyCache`, removed by MongoDB when old: tree id 30 days, item specifics and category info 7 days, the category suggested for a title 14 days, keyed by the search words, so a second product with the same words costs nothing); callers that ask for the same thing at the same moment (a big publish of one category) share ONE call; an error is never kept. Each call to eBay is counted in `ApiUsage` under the key `taxonomy:YYYY-MM-DD` (Pacific day). When eBay answers that the limit is reached (HTTP 429 or "limit reached"), nothing more is sent for 10 minutes and the seller sees "eBay's daily limit for category lookups is used up. It starts again at midnight Pacific time (about 12 noon in Pakistan). Try again then." Cached answers keep working. A raised limit needs eBay's Application Growth Check (Developer Portal), which is eBay's decision, not something the code can speed up.

## Net Profit sheet (sidebar "Net Profit")

One line per order (`GET /api/net-profit`, newest first, 1000 lines at a time; `GET /api/net-profit/export` = a real .xlsx file; `PATCH /api/net-profit/:id` saves the two typed cells, and the Orders page can save them too - see "Orders" below). The seller types **BUYING PRICE** (named "Amazon price" before; `Order.sheetAmazonPrice`, `amazon_price` / `amazonPrice` in the data, empty until typed: never taken from the listing, and separate from the Orders page's own "Cost per item") and **ORDER EARNING** (`Order.orderEarning`, "Order earnings" in Seller Hub); the rest is worked out: EBAY PRICE = the order line's item price, PROFIT = EBAY PRICE - BUYING PRICE, EBAY COST = EBAY PRICE - ORDER EARNING, NET PROFIT = ORDER EARNING - BUYING PRICE (what cannot be worked out yet is empty, never 0). Every price is for the whole order line (an order of 2 pieces is one line). A net profit typed in the first version of the sheet (`Order.netProfit`) is kept and shown until both figures are typed. The dashboard's Net profit section adds the same per-order net profit (`GET /api/net-profit/summary`). All money is worked out in whole cents (`services/netProfitService.js`), totals are per currency. **Free accounts** reach only `netProfitFreeLines` lines (Admin -> Limits, default 1000, checked on the server, also for the export); an account with a running plan (a plan name that has not ended, or an admin) has no limit and "Add lines" adds 1000 more each time.

**The export is a real .xlsx workbook now, not CSV** (`services/netProfitXlsx.js`, built with `exceljs`, streamed straight to the response the same way the CSV version paged through the lines - never held whole in memory, so a paid account's full history exports the same way a free account's capped one does). It has every column plus quantity, date, store, item number and ASIN, and the total rows at the end, plus what CSV cannot carry: the header row is bold with a coloured fill, the **Net profit** column's text is green for a positive line and red for a loss, and every money cell is formatted in its own row's currency **sign** (`$`, `£`, `€` ...) directly on the number - there is no separate "Currency" text column any more (it said the same thing twice); a currency this table has no sign for still shows its code on the money cell, never blank.

## AI category backup (eBay's category limit used up)

When eBay's Taxonomy limit is reached, category suggestions stop for everybody until midnight Pacific. The backup lets the AI choose the category from a **real list** instead: **Admin Panel → Categories** takes eBay's "Category IDs" CSV (columns `CategoryID`, `Category Path`) for each eBay site (`ebay.com` = EBAY_US, `ebay.co.uk` = EBAY_GB, ...); uploading again replaces that country's list, "Remove" deletes it. The rows are stored in MongoDB (`EbayCategoryList`, one gzipped document per marketplace).

- eBay's own suggestion is always tried first. Only when eBay says its limit is reached, and the seller's marketplace has a list, `services/aiCategoryService.js` runs: `services/categoryListService.js` finds the ~40 categories that look like the title, the AI (Anthropic, the model set in Admin → AI) chooses ONE of them, and an ID that is not in the list is never accepted. If nothing fits it looks once more with the words the AI used for the product.
- It is used where a draft with no category is published (`services/draftCategoryService.js`). The Drafts page's own suggestion boxes are unchanged (they run just by looking at the page, so they never spend credits).
- The seller pays **Admin → AI → "AI category" credits** (also in Credit costs, key `AI_CATEGORY`, default 1), charged first and given back when no category is found. The same product words asked again within 24 hours cost nothing. Switch: Admin → AI → AI category. It needs `ANTHROPIC_API_KEY`.
- Item specifics still come from eBay's Taxonomy API (kept per category for 7 days), so a NEW category can still stop at that step on a day the limit is used up; the category stays saved on the draft and the next publish continues.

### Drafts: "Fill category with AI", fast delete, import progress

- **Fill category with AI** (Drafts -> select -> bulk bar, `POST /api/listings/bulk-category`, 20 per request): the AI chooses the category of every selected draft that has none, from the category list of THAT draft's own eBay site (a US store's draft from the US list, a UK store's from the UK list; the site is the draft's, else its store's, and is never guessed: a draft with no known site is skipped). It does not ask eBay, so it costs none of eBay's category limit. Costs the admin-set `AI_CATEGORY` credits per draft that gets a category (skipped / failed / already-has-one are free); a marketplace with no uploaded list is skipped with the reason.
- **Bulk delete** (`POST /api/listings/bulk-delete`, at most 5000 per request; the page sends 1000 at a time): one query finds the listings and ONE `deleteMany` removes every one without an eBay offer (it used to read and delete one by one, minutes for thousands). A listing that has an eBay offer still has the offer ended first (4 at a time) and stays when eBay refuses. The Drafts page removes the cards at once and shows "N deleted · M drafts left" at the top.
- **"Importing X of Y products"** (top of Drafts during a bulk import): the job's `done` / `failed` counts are now written after every chunk of 20 products (`jobs/bulkImportProcessor.js persistCounts`), not only when a whole run ends, so the line moves while the drafts appear (it used to say 0 while 200 drafts were already saved).

## "Mark as ordered" (Orders): delivery date, buying price, order earning, and the note in ELMS and on eBay

"Mark as ordered" opens a window: the **delivery date** (when the parcel arrives; optional, can be in the future) and, both optional, the **buying price** and the **order earning**. `POST /api/orders/:id/ordered { ordered, deliveryDate, buyingPrice?, orderEarning? }` (`markOrdered` in models/ordersModel.js) sets the ordered step, `Order.orderedAt` (the moment it was marked) and `Order.deliveryDate` (noon UTC; null clears it, not given keeps it), writes the two figures to the Net Profit sheet (only the ones given; eBay cost and net profit are worked out from them), and adds **"ELMS: ordered, delivery 30 Sep 2026"** (just "ELMS: ordered" without a date) after the seller's own text in the order's **private note in ELMS** (Order.sellerNote). Saving again with another delivery date REPLACES the old mark; Undo (`ordered: false`) takes out only the mark and clears both dates. An order that is already shipped answers 409. The mark text is one rule for both notes (`services/orderNoteMark.js`; a mark written by the first version, "ELMS: ordered 27 Sep 2026", is understood too).

### Also on eBay (a switch in the Orders toolbar, off by default)

Orders has a switch "Also write "ordered" in the eBay note" (per seller, `User.ebayOrderNote`, `GET/PUT /api/orders/ebay-note-setting`; **off** until the seller switches it on). With it on, "Mark as ordered" (and Undo) also calls `POST /api/orders/:id/ebay-note` in the background (`services/ebayOrderNoteService.js`), and the ELMS mark never depends on it:

- eBay's Trading API has the call for it, the newer Fulfillment API does not. **GetMyeBaySelling** (SoldList, `AwaitingShipment`, up to 3 pages of 200) finds the order line (item number AND order number must agree, never a guess) and reads the private note on it; **SetUserNotes** then writes it back. SetUserNotes REPLACES the whole note (255 characters at most), so the seller's own text is kept and "ELMS: ordered, delivery 30 Sep 2026" is added after it; Undo takes out only that mark (the note is deleted when nothing else is left). If the current note cannot be read, nothing is written.
- Costs 2 Trading calls per mark, taken from the daily budget (`ebayCallBudget.reserve('note')`); when the budget or eBay's own limit is used up the note is skipped with a message.
- The result is kept on the order (`ebayNoteAt`, `ebayNoteError`) and shown in the order window.
- **NOT verified against the real eBay**: where eBay puts `PrivateNotes` in the answer (read tolerantly inside each transaction), whether the order number of the Fulfillment API equals the Trading OrderID, and whether this note is the "personal note" Seller Hub shows on the order. **Try it on ONE real order** (switch on in Orders, mark an awaiting-shipment order, open it on eBay) and read `[ebay-note]` lines in the Render log if it says "not changed".
- If the eBay note is "not changed", the reason is kept on the order and shown in its window (with a "Write the eBay note now" button); it says what eBay showed (how many order lines its awaiting-shipment list had, and the order numbers it has for the item), so the cause can be read there or in the `[ebay-note]` lines of the Render log.

## Live listings: paging, slim rows, search and sort on the server

The Live listings page used to load every listing at once (`GET /api/listings`), which took 1-2 minutes with a few thousand listings. It now asks the server for one page at a time and only the fields the list shows:

- `GET /api/listings?status=&accountId=&q=&sort=&vero=1&page=1&limit=50` answers `{ listings, total, page, limit, pages }` (page from 1, limit 1-200, default 50; the page asks for the next one as the seller scrolls or turns pages). A status or store id that does not exist answers an empty list at once (never "every listing"). Search (`q`) and the status/store filters run in MongoDB, not in the browser.
- A row (`models/listingsModel.js` `PAGE_SELECT`) carries only what the list shows: id, title, first image, price, Amazon price, status, store, SKU, ASIN, sold count, views, watchers, `updatedAt`. No description, bullet points, specifications, item specifics or the rest of the pictures — those add up fast over a few thousand rows and the list never displays them. `importId` is populated with only `asin amazonUrl amazonPrice product.price`. Every read uses `.lean()`.
- The editor (Edit button) reads the one listing it opens with `GET /api/listings/:id?full=1` (`getListingFull`), which brings back everything the old list used to carry.
- Sorting newest / price / views / watchers / stock is done by MongoDB; profit and sold count (worked out from other fields, or from a separate collection) are sorted by reading one light page of candidates and ordering it in Node (`COMPUTED_SORTS`), with a stable tie-break by `createdAt` so a page does not repeat or skip rows when the seller turns the page.
- `claimUnassignedListings` (attaches listings that were imported before a store was connected) used to run on every list read. It now runs only when there is something to claim: `Listing.exists({ userId, status: 'draft-import' ... })` (or similar) is checked first and a "nothing to claim" result is kept in memory for 10 minutes, and it also runs once right after a store is connected (`claimAfterStoreConnected`, called from `ebayAccountsModel` after `EbayAccount.create`) so a listing is never left unclaimed for up to 10 minutes.
- `getSoldByListing` (units sold, used for the Sold tab and the SOLD figure) is now asked only for the listing ids on the current page, not the seller's whole catalogue.
- VeRO (words that could mean a brand dispute) is scanned on the server, in the title and description (and the bullets, specifications, item specifics), with a 2-minute cache per seller (`scanVero`); the cache is cleared when a listing is saved (`clearVeroCache`, called from `updateListing`) so an edited listing is checked again straight away. The VeRO filter (`vero=1`) and the ⚠ count are both worked out from this.
- New indexes (`Listing`: `{userId,ebayAccountId,status,updatedAt}`, `{userId,status,createdAt}`, `{userId,ebayAccountId,status,createdAt}`; `Order`: `{userId,listingId}`) so a page, a sort and the profit/order lookups do not scan the whole collection.
- Above the list: `GET /api/listings/summary?accountId=` gives the tab counts (All / Active / Sold / Ended / Issues) and the totals (units sold, views, watchers, average margin, last synced) worked out on the server, so the page does not have to load everything to show them.
- "Select all N" (every listing of the current view, on every page) reads only the ids: `GET /api/listings/ids?status=&accountId=&q=&vero=1` (at most 20,000). Change price on a selection that spans pages reads the live rows of exactly those ids with `POST /api/listings/rows { ids }` (at most 5,000) — the ids are never cut down to one page's worth.
- `GET /api/listings/export?status=&accountId=&q=&vero=1` makes the CSV on the server (title, SKU, price, quantity, category, status), a batch of rows at a time, with a byte order mark and a formula guard, instead of the page building the file from what it had already loaded.
- The search box and the status tabs now send a request to the server (search is debounced 300 ms so typing sends one request, not one per keystroke); the page size shown stays 12 rows at a time in the UI (the server's own default page is 50, fetched ahead so scrolling and "load more" feel instant).

## CJdropshipping: a second, separate product source next to Amazon

CJdropshipping is a second supplier, alongside Amazon, with its own connect flow, import, and stock/price monitoring. **Every Listing and Import row says which source it came from** (`sourcePlatform`, `'amazon'` or `'cj'`), and the two never share a field, an API call or a credit key - see `models/schemas/Listing.js` for the full list of CJ-only fields (`cjProductId`, `cjVariantId`, `cjShippingCost`).

- **Migration**: existing rows predate `sourcePlatform` and are missing it outright (a schema default is never applied by Mongoose to a document already in the database). `db.js` `migrateSourcePlatformDefault` backfills every Listing and Import that is missing the field to `'amazon'` - it runs automatically on every server start, like the other index/data migrations in that file, and is idempotent.
- **Connect**: Settings -> "CJdropshipping" (its own card, separate from the eBay stores card). The seller pastes their own CJ API key (Admin cannot set this - it is per seller, like an eBay account); `services/cjAdapter.js` `connect` exchanges it for a CJ access/refresh token pair (`POST /authentication/getAccessToken`) to validate it before saving, then everything - the key and both tokens - is encrypted at rest (`services/cryptoService.js`) on `User.cj`. Nothing about the connection (not even whether it exists) is guessed: `GET /api/cj/status` / `models/usersModel.js` `isCjConnected` answer only `{ connected, connectedAt }`, never the key or a token. Disconnect (`POST /api/cj/disconnect`) logs out with CJ best-effort, then clears the stored credentials regardless of whether that call succeeded.
- **Rate limit**: CJ's own limit is 1 request/second for a Free-tier account (CJ docs -> Interface Call Restrictions). `services/cjAdapter.js` queues every call **per seller** (their own CJ account), spaced `CJ_MIN_INTERVAL_MS` apart (default 1100ms) - one seller's calls are never slowed by another's, but a single seller's own calls always are. The access token (life 180 days) is refreshed a day before it expires, never on every call, since the token endpoint has the same 1/second limit.
- **Import**: Import page -> the "CJdropshipping" tab (a fully separate section from the "Amazon" tab, never mixed on screen). Either paste a CJ product ID/SKU/link (`GET /api/cj/product`; a product with several variants shows a picker - colour/size, price, stock - before anything is saved) or search the CJ catalog by keyword (`GET /api/cj/search`, CJ's `product/listV2`). `POST /api/cj/import { pid | productSku | variantSku, vid? }` then saves it as an import + draft (`services/cjImportService.js` `saveCjProductAsDraft`, the CJ counterpart of `routes/fetchProduct.js` `saveProductAsDraft`), charging `ACTION_COSTS.CJ_IMPORT` (never `AMAZON_IMPORT`; separately editable in the Admin Panel like every other credit cost).
- **SKU and duplicate checks are per source**: a CJ listing's eBay SKU is `"CJ-"` + the CJ variant's own id (`cjVariantId`, e.g. `D4057F56-3F09-4541-8461-9D76D014846D`) - never the supplier's own variant SKU text, which can be any length, character set or shape (`services/skuService.js` `cjSkuFor`; also capped at eBay's 50-character sku limit, `finalizeEbaySku`, as a last-mile safety net at publish time - a long/odd supplier sku sent to eBay as-is used to make every CJ publish fail). The `"CJ-"` prefix is what keeps it from ever colliding with a 10-character Amazon ASIN sku in the same `{userId, ebayAccountId, sku}` unique index. "Is this already imported into this store" is checked by `cjProductId` + `cjVariantId` (`models/listingsModel.js` `findCjListingInStore`), a completely separate lookup from the Amazon one (`findListingInStore`, by asin/sku) - an Amazon id is never mistaken for a CJ one, or the reverse.
- **Profit**: a CJ listing's own shipping cost, quoted once at import time and refreshed by the stock/price monitor (`services/cjAdapter.js` `calcFreight`, CJ's `logistic/freightCalculate`, the cheapest of the quotes it returns), is kept on `Listing.cjShippingCost` and added into the cost basis by `listingProfitAmount`'s `extraCost` parameter (`models/listingsModel.js`, mirrored client-side in `listingProfit` in `index.html`). It is always 0 for an Amazon listing, so **Amazon profit is worked out exactly as it always was**.
- **Stock and price monitoring**: `jobs/stockMonitor.js` branches every published listing by `source_platform` before doing anything else. A CJ listing goes through `checkCjListing` (its own function, using only `services/cjAdapter.js`, never Canopy/Easyparser) and its own credit key `ACTION_COSTS.CJ_STOCK_MONITORING` (never `STOCK_MONITORING`/`PRICE_MONITORING`): it sums CJ's inventory across every warehouse (not just the buyer's country - CJ ships cross-border), ends the eBay listing when that total is 0, otherwise syncs eBay's quantity to CJ's **real** number (Amazon only ever gives in/out of stock, so that path still keeps a conservative 1) and reprices from the CJ price plus a refreshed shipping quote, keeping the seller's saved margin or pricing rule exactly like the Amazon price monitor does.
- **UI**: a source badge ("Amazon" / "CJ", `sourceBadgeHtml` in `index.html`) is shown on every draft and listing card, with a "Every source / Amazon / CJdropshipping" filter on both the Drafts page (filtered client-side, like its other filters) and the Live listings page (`source=` on `GET /api/listings`, `/ids` and `/export` - never on `/summary`, so the tab counts stay whatever they always were, the same way the search box and the VeRO filter already do not change them). A CJ row shows its own SKU as a plain chip rather than a link: CJ's storefront product URL format is not in its API docs, so ELMS never guesses one - only the API endpoints used above are real, confirmed CJ URLs.
- **Not built yet (by design)**: CJ auto-ordering. When it is built, only a listing with `sourcePlatform: 'cj'` may create a CJ order, and each eBay order may create at most one. A category picker for the CJ search (keyword search only today) and a category browse UI are also not built.
- **NOT verified against the real CJ API**: everything above was built from CJ's published API documentation (developers.cjdropshipping.com) and tested against a fake standing in for it - **no call in this feature has been run against a real CJ account**. Before relying on it: connect ONE real CJ account in Settings, import one product (try a multi-variant one, to see the variant picker), publish it, and watch the Render log for `[cj]` lines (a failed freight quote logs `[cj] freight quote failed for <vid> -> <country>: <message>` and is treated as "unknown", never as a reason to fail the import or the stock check). The next stock/price check for it can be watched the same way, under `[cj-stock-monitor]` / `[cj-price-monitor]`.

## AliExpress: account connection + product import (order-sync not built yet)

Unlike CJ (a pasted API key), AliExpress uses a real OAuth flow: ELMS has its own AliExpress Open Platform app (`ALIEXPRESS_APP_KEY`/`ALIEXPRESS_APP_SECRET`, developers.aliexpress.com - the owner's app, not a per-seller key), and each seller signs in on AliExpress's own consent screen to authorize it. A third product source next to Amazon and CJ - see `models/schemas/Listing.js` for the full "never mix" rule this whole feature follows (`aliexpressProductId`/`aliexpressSkuId`, its own `sourcePlatform: 'aliexpress'`).

- **Env vars to set on Render**: `ALIEXPRESS_APP_KEY`, `ALIEXPRESS_APP_SECRET`, and either `ALIEXPRESS_REDIRECT_URI` (the full callback URL) or `BACKEND_PUBLIC_URL` (already set for image hosting - the callback path is appended to it automatically). **Register this exact URL as the app's OAuth redirect/callback URL in the AliExpress App Console**: `{BACKEND_PUBLIC_URL}/api/aliexpress-connect/callback`.
- **Protocol**: AliExpress Open Platform uses Alibaba's IOP protocol (the docs' own SDK examples are Java/PHP/.NET/Ruby/Python; there is no Node.js SDK, so `services/aliexpressAuthService.js` calls the plain HTTP form of it). Request signature: sort every param except `sign` by name, concatenate as `name+value` back to back, prefix with the API path for a system-tool API (`/auth/token/create`, `/auth/token/refresh`), then `HMAC-SHA256(appSecret, thatString)` as **hex, uppercase** - taken directly from the docs' own CURL example, not guessed.
- **Connect flow** (`routes/aliexpressConnect.js`): `GET /api/aliexpress-connect/start?token=` (a direct browser navigation, never fetched - see below for why) redirects straight to AliExpress's consent screen; the seller signs in there and is redirected to `/api/aliexpress-connect/callback?code=...` (code expires in 3 minutes), which exchanges it for an access/refresh token pair (`POST /auth/token/create`) and saves it encrypted at rest on `User.aliexpress` (`services/cryptoService.js`, same as CJ). `POST /api/aliexpress-connect/disconnect` clears it.
- **The "state" problem - confirmed against a real app, and fixed**: AliExpress's authorize URL has no `state` parameter, and (confirmed against a real AliExpress app) `redirect_uri` must match the App Console's registered callback URL **exactly** - appending `?state=...` to it was rejected with `Redirect uri does not match the callback url of the APP`. So `redirect_uri` is always the bare, fixed URL, and which ELMS user is mid-connect is carried in a short-lived, HttpOnly, `SameSite=Lax` cookie (`ae_connect_state`) instead: `/start` sets it right before redirecting to AliExpress, `/callback` reads it back and clears it. This only works because the browser reaches `/start` by a genuine top-level navigation (the frontend button does `window.location.href = ...`, never a `fetch`) - a cookie set via a cross-origin `fetch` response would not reliably survive the same way.
- **Import** (`services/aliexpressAdapter.js`, `services/aliexpressImportService.js`, `routes/aliexpress.js`): Import page -> the "AliExpress" tab. Paste a product ID or a full `aliexpress.com/item/...` link (`GET /api/aliexpress/product`; a product with several sku options - colour/size - shows a picker before anything is saved, using `aliexpress.ds.product.get`). `POST /api/aliexpress/import { productId | url, skuId? }` saves it as an import + draft, charging `ACTION_COSTS.ALIEXPRESS_IMPORT` (never `AMAZON_IMPORT`/`CJ_IMPORT`). Token refresh (30-minute margin, concurrent calls share one refresh - see `aliexpressAdapter.ensureToken`) happens automatically before a fetch if needed.
- **⚠ Unverified assumption - the business-API call shape**: the docs' own examples for `aliexpress.ds.product.get` are Java/PHP SDK calls (`IopClient.execute(request, accessToken, Protocol.TOP)`), not a raw HTTP example the way `/auth/token/create` got a CURL sample. `services/aliexpressAuthService.js callBusinessApi` calls `POST /sync` with the API name in a `method` param and the access token in a `session` param - the standard shape across Alibaba's IOP/TOP-protocol platforms (CJ/Lazada/Taobao) - but this has **not been confirmed against a real AliExpress call**. If the very first real product fetch fails with a signature or "invalid session" error, check this shape first against AliExpress's own "System Parameters"/business-API-call documentation.
- **SKU and duplicate checks are per source**: an AliExpress listing's eBay SKU is `"AE-"` + the AliExpress sku's own id (`aliexpressSkuId`, AliExpress's `sku_id`) - never the supplier's own `sku_code`/barcode text, the same rule `cjSkuFor` already follows (`services/skuService.js` `aliSkuFor`). "Is this already imported into this store" is checked by `aliexpressProductId` + `aliexpressSkuId` (`models/listingsModel.js` `findAliexpressListingInStore`), separate from the Amazon and CJ lookups.
- **UI**: the source badge (`sourceBadgeHtml` in `index.html`) adds an "AliExpress" colour; the "Every source" filter (Drafts and Live listings) adds an `aliexpress` option.
- **Not built yet (by design)**: stock/price monitoring (a published AliExpress listing is simply skipped by `jobs/stockMonitor.js`, the same safe fallback an ASIN-less listing already gets - never a crash, never a wrong Amazon check), AliExpress auto-ordering, a keyword/category search of the AliExpress catalog (the docs given for this feature covered `aliexpress.ds.product.get` only, no search API).
- **NOT verified against the real AliExpress API**: everything above was built from AliExpress's own published API documentation (developers.aliexpress.com, pasted in full during this feature's build) and tested against a fake standing in for it - **no call in this feature has been run against a real AliExpress account**. Before relying on it: connect ONE real AliExpress account in Settings, import one product (try a multi-sku one, to see the option picker), publish it, and watch the Render log for `aliexpress` lines. The two ⚠ items above (the OAuth `state` round-trip, and the business-API call shape) are the most likely first failure points.

### Order-status push notifications (the message-push webhook)

This is a **separate callback from the OAuth one above** - register it in the AliExpress App Console under "Message Subscription and Callback URL" (not the app's "redirect_uri"/"Auth" field): `{BACKEND_PUBLIC_URL}/api/aliexpress/webhook`.

- `routes/aliexpressWebhook.js` / `services/aliexpressWebhookService.js`: acknowledges every message with a plain `200` (status code only, no body, per the docs) **before** doing anything else, since AliExpress requires the ack within 500ms and retries (up to 12 times, 30 minutes apart) on a slow or missing one. The `Authorization` header is verified when present (`HEX_ENCODE(HMAC-SHA256(AppKey + messageBody, AppSecret))`, lowercase hex - the docs' own Java sample, a **different, unrelated signature scheme** from the uppercase-hex one `services/aliexpressAuthService.js` uses to sign outgoing API calls) and rejected with `401` if it does not verify; a message with no `Authorization` header at all is still accepted, since the docs call the signature "not mandatory, but highly recommended."
- Needs the exact raw request body for that signature check, so it is mounted in `server.js` **before** the global `express.json()`, with its own `express.raw()` - same reasoning as the Paddle/CashTap/eBay webhooks already there.
- **What it does today: only logs the message** (`[aliexpress-webhook] seller ...: <type> (message_type=N)`), nothing more. It does not link a message to an ELMS order or listing, because AliExpress auto-ordering (ELMS placing an AliExpress order for a buyer's eBay order) is not built - there is no ELMS-side "AliExpress order" yet for a push message to update. Wiring real order-state updates onto this is a follow-up once auto-ordering exists.
- This endpoint needed no seller session/auth of its own to build or test (it is secured by the signature, not a login), so it works as soon as it is deployed - registering the URL and sending AliExpress's own "TEST AE PUSH" from AppConsole should get a `success` immediately, unlike the OAuth flow and the product import above, which both need real credentials to try.

## Buyer-facing order tracking page (elmstool.com/track/&lt;code&gt;), via 17TRACK

A public page (no sign-in) where a buyer can check an order's delivery status without ever seeing the real tracking number, carrier, or which supplier (Amazon/AliExpress/CJ) it shipped from. Built on [17TRACK](https://api.17track.net/en/doc)'s Tracking API, since ELMS has no carrier integrations of its own.

- **Env vars to set on Render**: `TRACK17_API_KEY` (17TRACK dashboard -> account -> your security/API key) and `TRACK17_WEBHOOK_SECRET` (any random string you make up yourself - see below).
- **How a code is made**: `PUT /api/orders/:id/tracking` (the seller saving an order's tracking number - `routes/orders.js`, unchanged otherwise) now also calls `models/trackingLinksModel.js` `createOrGetForOrder`, which registers the real number with 17TRACK (`services/track17Service.js registerTracking` - carrier is auto-detected, 17TRACK hands back its own numeric carrier code) and makes a short public code (`ELM` + 5 digits) stored on a new `TrackingLink` document (`models/schemas/TrackingLink.js`) alongside the real number/carrier. Re-saving the same order with the same tracking number reuses the existing code rather than registering it again. If 17TRACK's registration call fails (bad number, rate limit, etc.) the code is still created - the tracking page just shows "not available yet" until the seller corrects/re-saves the number.
- **Where the code is shown to the seller**: the PUT response includes `trackingCode`; `GET /api/orders/:id/tracking-link` returns the existing one (`{trackingCode}`, or `null`) for when the order is reopened later without re-saving tracking.
- **The public page** (`GET /api/track/:code`, `routes/publicTracking.js`, no auth): looks up the code, and if the cached status is missing or more than an hour old, asks 17TRACK live (`getTrackInfo`) and caches the answer. **Only ever returns `{code, status, statusDetail, statusAt}`** - the real tracking number and 17TRACK's carrier code never leave this endpoint, by design (see the schema file's own comment).
- **The webhook** (`POST /api/track17-webhook/:secret`, `routes/track17Webhook.js`): register it in 17TRACK's dashboard (Settings -> Webhook) as `{BACKEND_PUBLIC_URL}/api/track17-webhook/{TRACK17_WEBHOOK_SECRET}`. 17TRACK does **not** sign these pushes (no HMAC scheme, unlike every other webhook in this app) - the random secret in the URL path is what stops someone else from posting fake status updates, so treat `TRACK17_WEBHOOK_SECRET` as a real secret, not a public value. Always answers `200` (even on our own errors), since a missed push is simply caught by the public page's own live-refresh fallback above.
- **Frontend** (elms-frontend repo): `track.html`, a public page (pattern-matched on `pricing.html`/`refund.html`) reached at `/track/<code>` via a Render Rewrite rule (`/track/*` -> `/track.html`, added the same way as `/refund` and `/plans`). No Amazon/AliExpress/CJ/carrier name is ever shown - just the order's status.
- **Rate limits (17TRACK's own)**: 3 requests/second, max 40 numbers per `/register` call (ELMS only ever sends 1 at a time here), about 400,000 registrations/hour capacity. 17TRACK re-polls each carrier itself every 6-12h (24h once delivered) - the public page's own 1-hour cache floor is well inside that, so it never asks 17TRACK more often than 17TRACK would have new information anyway.
- **NOT verified against a real 17TRACK account**: built from 17TRACK's own published API v2.2 documentation, not tried against a real tracking number yet. Before relying on it: save a real tracking number on one order, open its `/track/<code>` page, and confirm a status appears (may show "Pending" until 17TRACK's first poll, typically within a few hours) - then check the webhook by watching the Render log for `[order-tracking-page]` lines after a status changes.
